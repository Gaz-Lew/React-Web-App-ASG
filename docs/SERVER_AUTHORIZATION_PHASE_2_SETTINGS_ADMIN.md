# Server Authorization Phase 2: Settings/Admin

## Operations Audited

Low-risk callable candidates:

- `appSettings/config` updates through `updateAppSettings`.
- `settingsHistory` append records created as part of settings updates.
- Settings rollback writes from `SettingsHistoryPanel`.
- Configuration audit writes generated by settings update and rollback actions.

Medium-risk candidates:

- Rep admin metadata in `reps/{repId}`: role, active status, Firebase UID linkage, region, allowed regions, PIN, and admin-visible profile metadata. These should move behind focused callables after claim coverage is verified.
- Training course and module admin writes in `trainingCourses` and `trainingModules`. These already have elevated-role rule boundaries, but creation/edit/delete semantics are still client-authored.
- Document/template administration in `documentLibrary` and `formTemplates`. These are admin-sensitive but also touch storage/document UI flows, so they should be migrated separately.

Should remain client-side temporarily:

- Realtime operational workflows: leads, deals, chat, appointments, DRAPS, commissions, presence, notes, and document instances.
- Training session writes from active roleplay sessions.
- File uploads and storage-backed deletes until the associated Storage rules and rollback behavior are reviewed together.

## Callables Added

- `updateAppSettingsCallable`: requires authenticated admin-or-higher claims, validates known settings sections and fields, writes `appSettings/config`, appends `settingsHistory`, and adds a server-attributed audit entry.
- `rollbackAppSettingsCallable`: requires authenticated admin-or-higher claims, validates the target settings snapshot, replaces `appSettings/config`, appends a rollback history entry, and adds a server-attributed audit entry.

Both callables use server timestamps and record Firebase UID, rep ID claim, role claim, provider, and `source: "callable"` for future rule and audit separation.

## Frontend Migration

- Phase 2 introduced callable-first settings writes for app settings updates and rollbacks.
- Phase 3 removed the temporary Firestore fallback for migrated settings, rollback, and audit helper flows.
- `appendAuditEvent` remains callable-first for audit writes.

## Future Rule Tightening

Phase 3 completed:

- `appSettings/config` direct client writes denied.
- `settingsHistory` direct client creates denied.
- `auditLogs` and legacy `audit` direct client creates denied.
- `settingsHistory` read remains authenticated to preserve the admin UI listener shape.

Future:

- Move rep admin metadata writes into dedicated callables before tightening `reps/{repId}` writes.
- Move `documentLibrary`, `formTemplates`, `trainingCourses`, and `trainingModules` writes in separate phases with storage behavior reviewed at the same time.

## Remaining Client-Authoritative Risks

- Admin metadata in `reps` can still be written directly by any authenticated client under current rules.
- `documentLibrary` and `formTemplates` remain authenticated-client writable.
- `trainingDocuments`, `trainingVideos`, and `trainingRecordings` remain authenticated-client writable for now.
- Legacy direct `auditLogs` writes from lead/client UI side-effects may now fail under rules; primary operational writes are intentionally unaffected.
